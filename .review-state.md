## Findings — Pass 1

### Bug 1 (HIGH) — Action input planes not rank-mirrored under color augmentation

**File**: `src/py/training.rs:160-170`
**Severity**: high — silently miscorrelates dynamics-network training inputs roughly half the time.

The new code replaces the old `encode_action_spatial(action)` →
`flip_action_planes(...) if apply_flip` pattern with:

```rust
let pov_white = if apply_flip { !step.white_to_move } else { step.white_to_move };
let encoded = encode_action_spatial_for_color(step.action, pov_white);
```

For **base actions** (`action < NUM_BASE_ACTIONS`, i.e. ~99% of moves),
`encode_action_spatial_for_color` ignores `pov_white` and reads `from_sq = action / 64`,
`to_sq = action % 64` directly from the action index. Result: the action input planes
contain the **un-flipped** from/to squares while the observation passed to `h(obs)`
has been rank-mirrored by `flip_obs_planes`. The pair fed to `g(hidden, action_plane)`
during the K-step unroll is therefore inconsistent on every `apply_flip=true` sample.

The old code path called `flip_action_planes(&encoded)` to rank-mirror the from/to
square one-hots, restoring (state, action) consistency. That step was dropped.

**Concrete trace** — `step.action=1` (a1→b1, white-to-move), `apply_flip=true`:

- Old: encode → planes[0]=1, planes[65]=1; flip_action_planes → planes[56]=1, planes[121]=1 (a8→b8, matching the rank-mirrored obs). ✓
- New: `encode_action_spatial_for_color(1, false)` → planes[0]=1, planes[65]=1 (a1→b1, NOT matching the rank-mirrored obs). ✗

The new test `test_flip_action_planes_matches_flip_action_invariant`
(`src/data/encoding.rs:898-980`) only verifies the helper-function
identity `encode(flip_action(a), !c) == flip_planes(encode(a, c))`; it does not
exercise the production path in `assemble_batch_arrays`. The existing
`test_value_target_sign_under_flip_matches_observation_pov`
(`src/py/training.rs:1435`) only asserts value-target signs.

**Fix sketch**: keep `pov_white = !step.white_to_move` under `apply_flip` for the
underpromo rank, _and_ pass the flipped action index for the base from/to:

```rust
let action_for_planes = if apply_flip {
    flip_action(step.action as usize) as ActionIndex
} else {
    step.action
};
let encoded = encode_action_spatial_for_color(action_for_planes, pov_white);
```

Add a regression test asserting that for a base action `a` and any `step.white_to_move`,
the produced `actions[bi, k]` planes under `apply_flip=true` are bit-equal to
`flip_action_planes(encode_action_spatial_for_color(a, step.white_to_move))`.

### Bug 2 (MEDIUM) — Same POV mismatch in Python TB encoder for Black-to-move positions

**File**: `python/hyzero/data/board_encoder.py:167-218`,
consumed in `tablebase.py:257` and `tablebase.py:401`.

`encode_action_spatial(action, white_to_move)` is the Python mirror of the Rust
`encode_action_spatial_for_color`. It has the same shape: for base actions it
reads `from_sq = action // 64`, `to_sq = action % 64` regardless of `white_to_move`.
TB positions with `board.turn == chess.BLACK` produce a rank-mirrored observation
(via `encode_board_python`, which sets `is_black=True`) but action planes that show
the absolute (un-mirrored) from/to squares.

For example, a black mate-in-1 position where Black plays e6e7: `action_from_move`
returns `from_sq=44, to_sq=52` (absolute). `encode_board_python` rank-mirrors the
board so Black's pieces appear on the bottom of the planes. `encode_action_spatial`
puts a `1.0` at planes[0,5,4] (from=44 → rank 5, file 4) and planes[1,6,4] (to=52),
but the rank-mirrored observation has Black's pieces around ranks 0-1, not 5-6.

The dynamics network sees a (state, action) pair where the action's "from" square
points to where the _opponent's_ pieces are in the mirrored frame. This silently
biases TB supervision against ~50% of positions (Black-to-move).

**Fix**: same as Bug 1 — for base actions, rank-mirror from/to when
`white_to_move=False`. Or, equivalently, change `action_from_move` to return a
POV-flipped action index for Black-to-move boards (matches the Rust convention
where `step.action` is stored in current-player POV in `game_task.rs:472-478`).

### Bug 3 (MEDIUM) — Diverse starts contaminate dual-evaluator (champion vs challenger) eval

**File**: `src/selfplay/game_task.rs:172-201, 245`

`init_self_play_board` is called from both `play_game` (self-play training) and
`play_game_dual` (champion-vs-challenger eval). When `HYZERO_STARTS_FILE` is set,
_both_ sample uniformly from the same FEN list.

Eval games are scored by champion win rate against `HYZERO_PROMOTION_THRESHOLD`
(default 0.55). The eval expects roughly equal-strength positions so that the
threshold reflects model strength delta. Sampling positions with `|Δmaterial| ≥ 2`
(per `build_starting_positions.py:108`) means the eval result is dominated by
_which side got the material advantage in the random sample_, not by which model
played better. With a 4-game-per-side budget this becomes very noisy and the
promotion signal degrades.

Additionally, the Black-to-move FENs (~50% of the random-play middlegame samples
and an unknown fraction of TB endgames) make the first move come from
`black_evaluator` rather than `white_evaluator`. Whether the caller's
"challenger=White, champion=Black" role assignment is honoured depends on
`side_to_move` from FEN parsing — it is, but the asymmetry between roles changes
per game.

**Fix**: have `play_game_dual` always start from the standard initial position
(or accept an explicit FEN list of _paired_ positions both evaluators play
both sides of).

### Bug 4 (LOW) — Diagnostic file `/tmp/hyzero_diag_probe.txt` grows unbounded

**File**: `python/hyzero/training/trainer.py:652-657`

```python
try:
    with open("/tmp/hyzero_diag_probe.txt", "a") as _pf:
        _pf.write(f"[diag_reached] step={self.model_version}\n")
        _pf.flush()
except Exception:
    pass
```

This append runs _every_ `train_batch` call. Over a long training run the file
grows by one line per training step (no rotation, no env-var gate). On a shared
training host `/tmp` accumulates state from multiple runs and is never cleaned up.

**Fix**: gate behind an env var (e.g. `HYZERO_DIAG_PROBE=1`), or remove — the
`_diag_print("[diag_reached] ...")` call on the next line already serves the same
purpose via stdout.
