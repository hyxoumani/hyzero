## Findings

### HIGH — pool filter excludes newest champion, second promotion falls back to win-rate gate

- `src/selfplay/pool.rs:19-45` (called from `src/selfplay/evaluation.rs:247-251`)
- `latest_archive_versions` is called with the current `champion_version` as the exclude arg. After the first promotion, the only archive on disk (`best_v{v}.pt` matching that champion) is filtered out, so the pool comes back empty and the code re-enters the bootstrap branch.
- **Impact**: the second promotion is decided by `win_rate >= 0.55` (default), not by the Elo delta gate. Contradicts the `run()` docstring at `evaluation.rs:222-224` which says the eval task "transitions to the Elo gate once `best_v001.pt` lands". Elo gating is effectively delayed until at least two archives exist, i.e. after the third promotion attempt.

### MED — silent no-op if opponent plumbing is missing

- `src/selfplay/evaluation.rs:341-376`
- When the pool is non-empty but `opponent_evaluator` or `opponent_server_handle` is `None`, the loop `continue`s and skips the promotion gate entirely.
- **Impact**: today `main.rs` always calls `.with_opponent`, so this is defense-in-depth. But any future plumbing regression silently freezes promotions instead of degrading to the win-rate gate.

### MED — composite SCORE hard-codes 1500.0 instead of `HYZERO_OPPONENT_INITIAL_ELO`

- `scripts/run_baseline.sh:249-251`
- If `HYZERO_OPPONENT_INITIAL_ELO` is overridden (e.g. `1600`), the runtime baseline moves but SCORE keeps subtracting `1500`, so an otherwise-unchanged candidate looks like it gained/lost ~100 Elo purely from config drift.

### LOW — `unwrap()` on poisoned opponent-handle mutex

- `src/selfplay/evaluation.rs:397`
- `opp_handle.lock().unwrap()` panics if the `std::sync::Mutex` is poisoned; the evaluation task then dies with no recovery. Guard is short-lived so poisoning is unlikely, but `if let Ok(guard) = opp_handle.lock()` would degrade gracefully.

### LOW — env-var parsing silently swallows bad input and skips bounds

- `src/bin/selfplay.rs::run_config_from_env`
- `HYZERO_POOL_SIZE`, `HYZERO_ELO_K_FACTOR`, `HYZERO_PROMOTION_ELO_DELTA`, `HYZERO_OPPONENT_INITIAL_ELO`: parse failures fall back to defaults with no log, and no bounds are checked. `HYZERO_POOL_SIZE=0` traps the run in bootstrap forever; `HYZERO_PROMOTION_ELO_DELTA<0` promotes anything; `HYZERO_ELO_K_FACTOR<0` inverts every update.
- Matches the repo's existing env pattern, so this is a category flag rather than a regression.
