## 🔴 Critical — POV mismatch in Python TB and dynamics-pretrain pipelines

The Rust self-play pipeline stores actions in **POV (rank-flipped) coordinates** for
Black-to-move steps (`src/selfplay/game_task.rs:463-467, 472-480`); `assemble_batch_arrays`
in `src/py/training.rs:160-170` then encodes spatial action planes from those already-flipped
indices. That is consistent with the rank-mirrored observation.

Every Python ingestion path that produces TB or pretrain training tensors uses
**absolute-square coordinates** for actions and policy/legal targets, yet feeds the network
the same rank-mirrored observation. Specifically:

1. `python/hyzero/data/tablebase.py:build_tb_batch_trajectories` (lines 392-401):

   ```python
   action_idx = traj.actions[k]                       # absolute-square index from action_from_move
   ...
   white_to_move = (board_k.turn == chess.WHITE)
   actions[i, k] = encode_action_spatial(action_idx, white_to_move)
   ```

   `encode_action_spatial` (board_encoder.py:210-216) does **no** rank flip for base actions;
   it only adjusts the inferred rank for under-promotions. So for any Black-to-move step,
   the action plane shows squares on absolute ranks 7/6 while the observation has the same
   pieces at rank-mirrored positions (rank 0/1).

2. Same path scatters policy / legal_mask targets at absolute action indices
   (lines 380-390, 404-407). The network's policy logits are produced from a
   rank-mirrored observation and are therefore in POV space; writing the target
   into the absolute index puts the correct probability at the **wrong** logit.

3. `build_tb_batch` (snapshot path, lines 252-285) has the same problem.

4. `scripts/pretrain_dynamics.py:60-78` repeats the bug for the SimSiam dynamics
   pretrainer:

   ```python
   action_idx = action_from_move(mv, board)     # absolute
   obs_before = encode_board_python(board)      # POV-flipped for Black
   action_planes = encode_action_spatial(action_idx, white_to_move)  # absolute
   ```

5. `scripts/build_tablebase_cache.py` and `build_tablebase_trajectory_cache.py`
   store all `mating_actions / optimal_actions / all_legal_actions / actions`
   as absolute indices (`action_from_move(m, board)`), so the bug is baked into
   any cache file already on disk.

### Why it matters

- Plane 101 (side-to-move) was removed in Phase 3b
  (docs/wiki/board-encoding.md, src/data/encoding.rs:9). The network has **no**
  signal letting it tell white-to-move from black-to-move from the observation
  alone. Replay rows give it (POV-obs, POV-action); TB/pretrain rows give it
  (POV-obs, ABSOLUTE-action). For ~50 % of TB/pretrain data the action plane and
  policy index mean the opposite of what the same observation would have meant
  in self-play. The two streams **contradict** each other, exactly the kind of
  collapse that motivated the value-head rescue work documented in the
  agent-memory tablebase reports.

- Underpromotion actions are unaffected (their encoding is file-only and
  color-invariant by design — `flip_action` is the identity for them).

- The rule `mcts-pov-symmetry.md` explicitly calls out POV-symmetric ordering
  for the Rust self-play side; the Python ingestion path needs the same
  contract.

### Fix sketch

Option A (preferred — keep the Rust convention): in board_encoder.py either
(i) call a `flip_action`-equivalent on `action_idx` when `white_to_move` is
False before `encode_action_spatial`, or (ii) make `encode_action_spatial`
itself rank-mirror `from_sq`/`to_sq` for base actions when not white-to-move.
Apply the same flip to scattered policy / legal-mask indices in
`build_tb_batch`, `build_tb_batch_trajectories`, and to action_from_move
results consumed in `pretrain_dynamics.py`.

Option B (less surgery): teach the Python side to keep absolute-coord actions
end-to-end and special-case the TB path in `Trainer.train_batch`. This is
asymmetric with Rust and risks the same mismatch resurfacing.

### Reproducer / regression test idea

Add a Python unit test that, for every action `a` and both colors `c`,
asserts:

```
encode_action_spatial(flip_action(a), not c)
== flip_action_planes(encode_action_spatial(a, c))
```

This is the Python analogue of `test_flip_action_planes_matches_flip_action_invariant`
in `src/data/encoding.rs:919-976`, which currently passes only because
`encode_action_spatial_for_color` in Rust is fed pre-flipped POV-space inputs.

Existing tests `test_trajectory_*` and `test_tablebase_*` use only
white-to-move FENs (`"... w - - 0 1"`), which is why the bug slipped through.

## 🟡 Medium — `select_action` near-zero temperature loses tie-break randomness

`src/mcts/tree.rs:609-628`. With `temperature = 0.01`, `inv_temp = 100`, and
realistic MCTS visit counts (≤ 800), `v.powf(100)` overflows to `+∞` for any
visit count above ~10:

- f32 max ≈ 3.4e38; `2.0_f32.powf(100) ≈ 1.27e30` (fine);
  `10.0_f32.powf(100)` overflows to `+∞`.
- With multiple `+∞` weights, `total = +∞`. `rand() * +∞` is `+∞` (or `NaN` if
  `rand()` returns 0.0). The first `cumulative >= +∞` check picks the
  first-encountered `+∞`, which is the **lowest-index** tied-max — exactly the
  failure mode the team just fixed in the temperature-zero branch.

`play_game_dual` calls `tree.select_action(0.01)` (game_task.rs:320) for eval;
`play_game` calls it after `temperature_moves` plies (game_task.rs:454-460).
At those points an undertrained network can easily produce many tied visit
counts. The greedy branch (`temperature <= EPSILON`) does the right thing and
should be reused for "near-greedy" intent. Either:

- Special-case `temperature < TEMP_GREEDY_EPS` (e.g. 0.05) to take the greedy
  branch with random tie-break, **or**
- Subtract `max_visits` from each `v` before exponentiating (log-sum-exp trick)
  so the weights stay representable.

This is the same class of bug as `mcts-pov-symmetry.md` rule 2 ("first-max
determinism produces systematic color dominance") and undermines that rule
for any non-zero temperature in eval.

## 🟡 Medium — `build_tb_batch` underpromo-slot decode allows out-of-range squares

`src/data/encoding.rs:163-167`. `decode_underpromo_action` extracts `to_file`
as `(remainder % 24) as u8` (range 0-23). For slots 8-23, `action_to_move`
later builds `to_sq = to_rank * 8 + to_file` and constructs a `Square::from`
with a value that can be ≥ 64. The path is unreachable from
`get_legal_moves` (which only emits to_file 0-7), but the function is `pub`
and the network can theoretically predict any of the 576 underpromo slots.
Defensive fix: clamp `to_file` to `< 8` and panic / return an error if it
isn't, or simply assert in `action_to_move`. `encode_action_spatial_for_color`
already guards (line 307-312); `action_to_move` does not.

`src/selfplay/game_task.rs:589-619` (`action_to_notation`) does clamp
(line 598: `let to_file = to_file_slot.min(7);`), so the in-game path is safe.
