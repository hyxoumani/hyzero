## Findings

### F1 — `_reinit_value_head` uses wrong Kaiming nonlinearity for hidden Linears

**File**: `python/hyzero/training/trainer.py`, `_reinit_value_head`
**Severity**: Minor (suboptimal init, no behavioral break)

```python
for i, m in enumerate(linear_layers):
    torch.nn.init.kaiming_normal_(m.weight, nonlinearity='linear')
```

`value_head` is:

```
Conv2d → BN → ReLU → Flatten → Linear(64,64) → ReLU → Linear(64,1) → Tanh
```

Both Linear layers get `nonlinearity='linear'` (gain=1). The first Linear is
followed by ReLU and should use `nonlinearity='relu'` (gain=√2). The final
Linear is followed by Tanh, for which `'linear'` is a reasonable approximation
(near the origin Tanh ≈ identity). Net effect: the first hidden layer starts
~√2× under-scaled. Won't break training, but the "reinit" is weaker than it
appears in the bias-offset experiments.

**Fix**: branch on `i == len(linear_layers) - 1` for `nonlinearity` selection
(same boundary already used for `bias_offset`).

### F2 — `build_tb_batch_trajectories` indexes `traj.legal_actions[k]` without length guard

**File**: `python/hyzero/data/tablebase.py:384`
**Severity**: Minor (defensive miss; can only fire on malformed cache)

```python
opt = traj.optimal_actions[k] if k < len(traj.optimal_actions) else []
if opt:
    ...
elif traj.legal_actions[k]:        # ← no `k < len(traj.legal_actions)` guard
    legal_k = traj.legal_actions[k]
```

`optimal_actions` has a length guard but `legal_actions` does not. If a cache
entry has shorter `legal_actions` than `k_steps + 1`, this raises `IndexError`.
The constructor (`TablebaseCache.__init__`) does not assert length parity
across the trajectory's parallel lists either.

**Fix**: mirror the optimal_actions guard, or assert lengths in `TablebaseCache`.

### F3 — TB cache path defaults disagree between trainer and builder script

**File**: `python/hyzero/training/trainer.py` (trainer side); `scripts/build_starting_positions.py`
**Severity**: Configuration footgun, not a bug per se

- Trainer: `HYZERO_TABLEBASE_CACHE_PATH` → defaults to `data/syzygy/cache.pkl`
- Starts builder: `HYZERO_STARTS_TB_CACHE` → defaults to `data/syzygy/cache_trajectories.pkl`

If a user follows the documented `HYZERO_TABLEBASE_PATH=… run` flow with default
paths, the trainer will look for `cache.pkl` even though the trajectory cache
script writes to `cache_trajectories.pkl`. Easy to misconfigure into "TB
supervision silently disabled".

**Fix**: align defaults (probably to `cache_trajectories.pkl` since trajectory
format is the recommended one), or document the disjoint defaults at the top of
the trainer's TB block.

### F4 — Step-1 reward loss includes ALL rows; step-k≥2 excludes TB rows

**File**: `python/hyzero/training/trainer.py`, training-step k≥1 block
**Severity**: Intentional but fragile

```python
if k >= 2:
    total_reward_loss += (per_sample_rwd * non_tb).sum() / non_tb_count
else:  # k == 1
    total_reward_loss += per_sample_rwd.mean()
```

Comment says "TB step-1 reward carries the real mating-action signal" — true
for **snapshot** TB (mate-in-1 at step 1) but NOT for **trajectory** TB (mating
step is variable across 0..K). For trajectory TB the mask is all-zeros so the
two branches are equivalent (`per_sample_rwd.mean() == sum / B`), so the
behavior is fine today. But if someone later sets `is_tablebase=True` for a
trajectory cache the step-1-only special case would silently double-count
absorbing zeros as real reward targets.

**Fix**: gate the special case on cache format (or remove the branch and let
mating-step-anywhere flow through the standard masked path; snapshot caches
will then have a slightly different scaling at step 1 but no incorrectness).

### F5 — Diverse-start games begin with `turn_count = 0` regardless of FEN ply

**File**: `src/selfplay/game_task.rs`, `play_game` / `play_game_dual`
**Severity**: Behavior shift to be aware of, not a bug

After `init_self_play_board`, `turn_count` starts at 0 even when the FEN is
mid-game (fullmove=20+). This drives:

```rust
let temperature = if turn_count < config.temperature_moves as usize { 1.0 } else { 0.01 };
```

…so every diverse start gets `temperature_moves` plies of high-temperature
exploration regardless of how deep into the position the FEN already is. The
board's `halfmove_clock` IS loaded from FEN (50-move rule is intact), but the
temperature schedule is independent.

This is plausibly intentional ("explore around each sampled start"), but is
worth noting because the score formula penalises `avg_game_length / 100`. If
diverse middlegame FENs add ~temperature_moves extra random plies on top of the
already-mid-game position, average game length will rise vs. the old standard-
start regime even when learning is equivalent. This may partly explain why the
TB+diverse-starts run (8.16) lags the no-TB baseline (14.51) — the average
game length difference appears in the score directly.

**Fix**: consider deriving the initial temperature `t = max(0, temperature_moves - estimated_ply)`
from the FEN fullmove, or just reduce `temperature_moves` when diverse starts are
on. Not a correctness fix, but it would let you isolate "did TB help?" from
"are diverse starts cheaper per game?"

### F6 — `init_self_play_board` swaps evaluator roles in dual-eval when FEN is black-to-move

**File**: `src/selfplay/game_task.rs`, `play_game_dual`
**Severity**: Methodology concern for eval ladder, NOT incorrect per se

```rust
let evaluator = if side_to_move == Color::White { &white_evaluator } else { &black_evaluator };
```

Pre-change, every dual-eval game had White=`white_evaluator`, Black=`black_evaluator`
starting from move 1. Post-change, if the sampled FEN is black-to-move, the
first move is played by `black_evaluator`. The role assignment is still by
COLOR (so black_evaluator plays black throughout the game), which is fine for
fair color rotation across the ladder — but the W/L counts now mix
"black_evaluator playing black from move 1" with "black_evaluator playing
black from move N". This is statistically fine if FEN sampling is balanced
(50/50 white-to-move vs black-to-move) but biases the ladder if it isn't.

**Fix**: in `build_starting_positions.py`, explicitly verify (or assert) the
white-to-move : black-to-move split is ~50/50 in the emitted FEN list. The
script samples from random-play positions at ply 15–25 which should be ~50/50
by construction, but a comment/assert would pin it.

### F8 — Underpromo padding slots emit "promotion flag on, from/to zero" — asymmetric encoding

**File**: `src/data/encoding.rs:295-316`, `encode_action_spatial_for_color`
**Severity**: Cosmetic; would only matter if the policy head ever puts mass on
padding slots (it shouldn't)

For underpromo `action` slots where `to_file >= 8` (illegal padding inside the
576-slot underpromo encoding), the new code zeros out from/to planes but still
sets the promotion flag plane to all-1. This is preserved-from-the-old-behavior
_and_ satisfies the flip invariant (since flipping all-zero stays all-zero,
and the promotion flag is constant-fill so it's flip-invariant). So the
regression test passes.

But: the network receives "promotion-flag set, no source, no destination" as
the action representation for these illegal slots. If any policy target ever
puts non-zero mass on a padding slot (it shouldn't — `move_to_action` never
produces one), training would drift toward associating the bare promotion flag
with… nothing. Negligible risk; flag for future cleanup.

**Fix (optional)**: zero the promotion plane too when `to_file >= 8`. The
test invariant still holds (all three planes flip-invariant when all-zero).

### F9 — `conditional_beta_enabled()` decision is per-trajectory, not per-step

**File**: `src/py/training.rs:215-220`
**Severity**: As-designed; flagged because it's an easy footgun

```rust
let effective_beta: f32 = if conditional_beta_enabled() && !sample.is_draw {
    1.0
} else {
    beta
};
```

`effective_beta` is then used for **all K+1 steps** of this sample. So in a
checkmate trajectory, the value target at step 0 (game start, root_value
typically near 0) becomes `1.0 * outcome_in_step_perspective` = ±1 immediately
— the network is trained to predict ±1 at the opening from no MCTS rollout
evidence. This is the intended behavior (you want the value head to extract
the outcome from the position), but it skips any bootstrapping via root_value
entirely.

Combined with `HYZERO_DECISIVE_SAMPLE_FRAC=0.25` (prioritised sampling), this
could amplify variance / instability. Not a bug, but document and stage.

**Fix**: none required. Consider documenting in CLAUDE.md alongside the other
beta variants.

### F10 — No regression test pins `init_self_play_board` with a black-to-move FEN

**File**: `src/selfplay/game_task.rs`
**Severity**: Test gap

The new function returns `(GameBoard, Color)` but no test covers the case where
the parsed FEN puts Black on move (which then exercises a code path that did
NOT exist before — `play_game` previously _always_ started with `Color::White`).
If a future refactor of the loop accidentally reintroduces `side_to_move =
Color::White` after init, all tests still pass.

**Fix**: add a unit test that calls `init_self_play_board` after setting
`HYZERO_STARTS_FILE` to a temp file containing a single black-to-move FEN, and
asserts the returned color is Black.

## What I verified is correct

- **MCTS backup recurrence**: `G_{k-1} = r_k − G_k`, stored Q perspectives, and
  test_backpropagate_includes_mating_reward — math and code agree.
- **Color-symmetric action encoding**: underpromo flip invariant holds for both
  legal-file and illegal-padding slots; base actions trivially symmetric.
- **Terminal reward POV**: `last.reward = game_outcome * (white_to_move ? +1 : -1)`
  matches the `root_value` convention (each step in its own STM POV).
- **TB trajectory routing**: snapshot caches set `is_tablebase=True` → step-1..K
  loss masked; trajectory caches set `is_tablebase=False` → full unrolled loss
  applies. Verified by reading both branches of `train_batch` and
  `build_tb_batch{,_trajectories}`.
- **legal_actions sort + random tie-break**: fix is consistent across
  `play_game`, `play_game_dual`, and `MCTSTree::select_action`. Statistical
  regression test (#[ignore]) exists.
