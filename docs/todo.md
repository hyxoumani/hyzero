# Remaining Chess Engine Implementation Tasks

This document outlines the key functionalities that still need to be implemented to complete the chess engine logic, building upon the foundational bitboard and modular piece move generation:

## 1. Sliding Piece Move Generation (Blocking Logic)

*   **Implement proper sliding piece attack generation for Bishop, Rook, and Queen.** The current implementations are simplified and do not account for pieces blocking lines of attack.
*   Consider using efficient algorithms such as:
    *   Iterating rays and checking for the first blocker.
    *   Pre-computed attack tables (for edges and empty boards, then combined with blockers).
    *   Magic Bitboards (an advanced technique for very fast sliding piece attack generation).

## 2. Board Structure and State Management

*   **Create a central `Board` struct** to manage the overall game state. This struct should include:
    *   Separate `Bitboard`s for each piece type and color (e.g., `white_pawns`, `black_knights`, `white_rooks`, etc.).
    *   Combined `Bitboard`s for all pieces of a given color (e.g., `all_white_pieces`, `all_black_pieces`).
    *   A `Bitboard` representing all occupied squares on the board (`all_occupied_squares`).
    *   `active_color`: To track whose turn it is.
    *   `castling_rights`: To track the availability of castling for both kingsides and queensides.
    *   `en_passant_target_square`: The square where an en passant capture is possible.
    *   `halfmove_clock`: For the 50-move rule.
    *   `fullmove_number`: The total move count.
*   **Implement methods within the `Board` struct** to:
    *   Apply a `Move` to update all internal bitboards and state variables.
    *   Possibly implement a method to undo a `Move` (useful for search algorithms).

## 3. Legal Move Validation and King Safety

*   **`is_king_in_check(color: Color) -> bool`**: Implement a function to determine if a given king (of `color`) is currently under attack by any opponent piece. This will involve:
    *   Identifying the king's position.
    *   Iterating through all opponent pieces.
    *   Using each opponent piece's `generate_pseudo_legal_moves_mask` to see if it targets the king's square.
*   **Legal Move Filtering**: Develop a robust mechanism to filter *pseudo-legal* moves (generated by individual pieces) into *legal* moves. A move is illegal if it:
    *   Leaves your own king in check.
    *   Exposes your king to a discovered attack.
    *   Is an invalid castling move (e.g., moving through check).
    *   This typically involves:
        *   Simulating each pseudo-legal move on a temporary board.
        *   Calling `is_king_in_check` on the temporary board to see if your king is attacked.
        *   Discarding any moves that result in your king being in check.

## 4. Game End Conditions

*   **Checkmate Detection**: Determine if the `active_color`'s king is in check AND there are no legal moves available.
*   **Stalemate Detection**: Determine if the `active_color`'s king is NOT in check AND there are no legal moves available.
*   **Draw Conditions**:
    *   Implement logic for the 50-move rule.
    *   Implement logic for threefold repetition.
    *   Implement logic for insufficient material.

## 5. Move Generation for Special Moves

*   Refine pawn promotion logic (currently a `TODO` in the `Pawn` module).
*   Refine castling logic within the King's move generation and integrate it with legal move validation.
