### Findings

#### H1 — TB action planes use absolute coords, not POV (HIGH, likely bug)

`python/hyzero/data/board_encoder.py:188-216` (`encode_action_spatial` base
branch). For BASE actions with `white_to_move=False`, the function uses
`from_sq = action // 64` and `to_sq = action % 64` directly without any rank
flip, even though `encode_board_python` rank-mirrors the observation to
current-player POV.

In Rust self-play, the action stored on each `StepRecord` is already
POV-flipped (see `src/selfplay/game_task.rs:402-419` — `legal_actions` are
flipped via `flip_action` for Black before being handed to MCTS, and
`selected_action` is one of those POV-flipped indices). So
`encode_action_spatial_for_color` receives a POV-coord action and produces
POV-coord planes that match the POV observation.

In Python TB, `action_from_move(move, board)` returns
`from_sq * 64 + to_sq` using python-chess's ABSOLUTE square indices (no
flip). When that absolute action is passed to `encode_action_spatial(..., white_to_move=False)`,
the planes land at absolute squares while the observation is rank-mirrored
to Black's POV. Trace example, Black plays e7-e5:

- Rust path: `selected_action = flip_action(3364) = 796`; plane bits at
  `(rank 1, file 4)` and `(rank 3, file 4)` — POV-consistent with the
  rank-mirrored obs.
- Python TB path: `action_idx = 3364`; plane bits at `(rank 6, file 4)` and
  `(rank 4, file 4)` — absolute, NOT consistent with the rank-mirrored obs.

The underpromotion branch (lines 190-209) IS POV-correct because it picks
ranks from a `white_to_move` table and only files from the action index.
The base branch is the bug; most TB optimal moves are non-promotion, so the
fraction of TB samples affected is large for any 3–5-man cache that draws
half its positions Black-to-move.

Effect: The dynamics network is trained on inconsistent (obs_POV,
action_absolute) pairs for ~half of TB samples, contradicting the
(obs_POV, action_POV) pattern from self-play.

Fix sketch: at the top of `encode_action_spatial`, when
`not white_to_move`, run `action = flip_action(action)` (port the Rust
helper) before the base/underpromo branch. Or pre-flip the action index in
`build_tb_batch{,_trajectories}` for Black-to-move FENs. Either preserves
the underpromo branch's existing POV adjustment.

No test catches this — every test in `python/tests/test_tablebase.py` uses
White-to-move FENs (look for `" w "` in the FEN strings; no `" b "` cases
exercised). Adding a Black-to-move TB regression test that asserts
`encode_action_spatial(absolute_a, False) ==
encode_action_spatial(flip_action(absolute_a), True)` for all base actions
would pin the fix.

#### M1 — Terminal-reward index off-by-one between Rust replay and trainer (MEDIUM, pre-existing)

`src/selfplay/game_task.rs:539-542` writes
`last.reward = game_outcome * last_side_sign` onto `steps.last_mut()` —
i.e. on the StepRecord that ENCODES the pre-mate position and whose
`.action` is the mating move. So the Rust convention is "reward stored at
step k = reward generated by action[k]" (out-going).

`python/hyzero/training/trainer.py:601-643` pairs
`predicted_reward = g(h_{k-1}, actions[k-1])` with `tgt_rewards[:, k]`.
That target is the reward of the (k-1 → k) transition, i.e.
`tgt_rewards[k] = reward INTO step k` (in-coming).

`scripts/build_tablebase_trajectory_cache.py:340` (`target_rewards[k+1] =
1.0` on the absorbing step after the mating move) and
`python/hyzero/data/tablebase.py:90-94` correctly use the INTO convention
matching the trainer.

When `replay_buffer.sample_batch` happens to draw a window whose last index
K is the trajectory's last step, `target_rewards[K]` carries the mating
reward but the trainer interprets index K as the reward of the
(K-1 → K) transition — i.e. it trains the dynamics to predict the mating
reward for the move BEFORE the mate. The same trajectory, the same
observation, but a target placed at the wrong index.

Severity is bounded because (a) only windows ending exactly at
`steps[T-1]` see the mismatch (1 in `(T-K)` window choices per
trajectory), and (b) the dynamics outputs near-0 anyway for the bulk of
non-terminal training examples. Still incorrect, and inconsistent with the
TB pipeline.

This bug pre-dates `ee132c4` — it was present at the commit that added
`last.reward` (`b5a550c`, the revert of outcome-value-targets). Flagged
because the canonical-MuZero-backup work in this commit makes the reward
plumbing more salient.

Fix sketch: append a synthetic "post-terminal" StepRecord with reward=0
EXCEPT have its `target_rewards[T]` carry the mating reward; or shift the
write — store the terminal reward at a NEW final step rather than on the
existing last step. Simpler: change `assemble_batch_arrays` to
`target_rewards[k] = steps[k-1].reward` (with k=0 → 0), aligning the index
to the trainer's convention. Whichever path is chosen, also update
`test_terminal_reward_in_step_pov_not_white_absolute` in
`src/py/training.rs:1342` and `test_terminal_reward_pov_conversion` in
`src/selfplay/game_task.rs:1174` to match.

#### L1 — Test env-var lock not held by all writers (LOW, test reliability)

`src/py/training.rs`. `reward_gamma_env_lock()` (line 1115) is documented
to cover `HYZERO_REWARD_OUTCOME_GAMMA`, `HYZERO_VALUE_OUTCOME_BETA`, and
`HYZERO_DISABLE_COLOR_AUG`. But:

- `test_value_target_outcome_blend_white_root` (line 991) calls
  `std::env::remove_var("HYZERO_VALUE_OUTCOME_BETA")` without holding the
  lock.
- Same for `test_value_target_outcome_blend_black_root` (line 1035) and
  `test_value_target_outcome_blend_root_value_preserved` (line 1075).
- `test_conditional_beta_decisive_uses_pure_outcome` (line 1234) DOES
  hold the lock and sets `HYZERO_VALUE_OUTCOME_BETA=0.3`.

If the test runner schedules these in parallel, the lock-held test can
flip the env mid-execution of a non-locked test and cause a flake. Tests
pass today because cargo's default parallelism may not race them, but
this is fragile.

Fix: every test that touches any of those three env vars must lock
`reward_gamma_env_lock()` for the same duration as the env mutation +
read.

#### L2 — `HYZERO_MCTS_TRACE` parsed two different ways (LOW, minor)

`src/mcts/tree.rs:33-39` (`trace_enabled`) accepts any non-empty
non-`"0"` value (so `"true"`, `"yes"`, `"1"` all enable).
`src/selfplay/game_task.rs:20-29` (`mcts_summary_enabled`) parses as
`u64` only — `"true"` does NOT enable summary writing but DOES enable
the per-sim trace. Same env name; consider unifying via a shared helper.

#### L3 — `_reinit_value_head` does not reset optimizer state (LOW, documented)

`python/hyzero/training/trainer.py:352-392` re-initializes the value
head's `Linear.weight` and `Linear.bias` in-place. PyTorch's AdamW state
(`exp_avg`, `exp_avg_sq`, `step`) is keyed by parameter object identity,
so the old momentum/variance survives the reinit. After load-checkpoint

- reinit, the first few training steps blend old momentum into freshly
  random weights — exactly the "stochastic reinit gotcha" the commit
  message references.

If this becomes a stability concern, drop and rebuild the optimizer state
for the value-head params (`optimizer.state.pop(p)` for each `p in
value_head.parameters()`), or pass a fresh AdamW for that param group.

#### L4 — Eval games inherit diverse starts (LOW, behavioral)

`src/selfplay/game_task.rs:245` (`play_game_dual`) calls
`init_self_play_board(...)`, which means `HYZERO_STARTS_FILE` redirects
EVAL games away from the standard initial position too. Eval signal then
becomes a function of the starts-file distribution. If the intent was
self-play-only diversity, gate diverse starts with a separate flag (or
require `play_game_dual` to always start from the standard position).
