## Project Overview

hyzero — a chess engine emulating MuZero. Rust core (game logic, MCTS, self-play
coordinator) bridged to a PyTorch neural-network layer via PyO3.

## Commands

```bash
# Build
cargo build --release

# Test
cargo test

# Lint/Format
cargo clippy
cargo fmt

# Run
cargo run --bin server                                # game server
cargo run --bin client                                # game client
cargo run --bin selfplay                              # self-play training loop
cargo run --release --bin perft -- <FEN> <depth>      # perft CLI
bash scripts/run_baseline.sh 1800                     # 30-min controlled baseline
```

## Architecture

- `src/pieces/` — bitboard move generation (bishop, king, knight, pawn, queen, rook)
- `src/game/` — board state, history, player abstraction, perft
- `src/mcts/` — Monte Carlo Tree Search (node, tree, PUCT, evaluator interface)
- `src/selfplay/` — self-play coordinator, inference backend, training pipeline, dual-model eval
- `src/data/` — board encoding, replay buffer, shared data types
- `src/session/` — game session management
- `src/py/` — PyO3 bridge to Python inference and training
- `src/bin/` — binary entry points (server, client, selfplay, perft)
- `python/hyzero/` — MuZero h/g/f model definitions, trainer, inference server

## Workflow (thin-orchestrator)

The orchestrator routes and evaluates. All source work — reads, edits, code analysis — happens inside subagents (`analyst` for read/research, `developer` for edits). The orchestrator never reads source or runs content-spilling Bash; hooks enforce this.

- **Research questions** → dispatch `analyst` (read-only, returns ≤20-line summary)
- **Implementation** → dispatch `developer` (worktree-isolated, runs tests, returns summary)
- **After developer dispatch returns** → invoke `/verify` (analyst reviews diff against rules; iterates with developer internally until APPROVE)
- **On `/verify` APPROVE** → user-gated wiki update (analyst writes `docs/wiki/{topic}.md` after `/approve-wiki`)
- **End of session (optional)** → `/compact` to drain orchestrator-level wisdom to wiki

## Orchestrator Principles

You are the orchestrator. You decide what to **do**; subagents decide what is **true** about the code.

**You do not:**
- Read source files >50 lines (hook-blocked by `read-route.sh`)
- Edit, Write, or MultiEdit any file (hook-blocked by `edit-route.sh`)
- Run content-spilling Bash: `cat`, `head`, `tail`, `less`, `more`, `git diff`, `git show`, `git blame`, `git log -p`, `grep -A/-B/-C`, `awk`, `sed`, `tee` (hook-blocked by `bash-route.sh`)
- Analyze code, review diffs, judge correctness directly

**You do:**
- Receive user prompts; clarify ambiguity before dispatching
- Dispatch `analyst` for research and review; dispatch `developer` for changes
- Receive ≤20-line summaries from subagents
- Evaluate outcomes (success / blocker / next step)
- Sequence multi-dispatch features
- Present summaries to user with explicit gates for substantive saves (wiki updates)
- Iterate (re-dispatch on REJECT, internally — user only sees final APPROVE)

**Allowed Bash in main session (state queries only):** `git status`, `git log --oneline`, `git rev-parse`, `git branch`, `ls`, `find`, `wc -l`, `grep -l`, plus the `Glob` tool for file paths.
